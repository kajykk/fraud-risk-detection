## 1. 风险评估概述

### 1.1 评估目的

- 系统识别 FRD 项目全生命周期内的潜在风险
- 量化风险概率与影响，明确优先级
- 制定可执行的应对策略与应急预案
- 建立风险监控与闭环机制

### 1.2 评估范围

- 项目级风险：进度、成本、资源、范围
- 技术风险：架构、性能、可靠性
- 业务风险：需求、用户体验、市场
- 合规风险：PCI-DSS v4.0、PIPL、反洗钱法、GB/T 22239 等保 2.0 三级
- 安全风险：数据泄露、攻击、滥用
- 运营风险：上线后稳定性、可维护性
- **AI Agent 协作风险（V1.1 新增）**：1 真人 + 11 AI Agent 模式特有的决策一致性、幻觉、上下文丢失、越权、知识过期、依赖死锁、成本失控等

### 1.3 评估时间

- 初评：2026-07-27（项目立项）
- 复评：每月一次（与月度评审同步）
- 专项评估：里程碑节点、重大变更、安全事件后

### 1.4 团队模式（V1.1 新增，对齐基准 §1）

本项目采用 **1 真人（邝振华，100% 投入，终审决策）+ 11 AI Agent（PM/REQ/ARCH/BE-1/BE-2/FE/ML/GNN/DevOps/QA/SEC）** 协作模式，外聘 QSA 顾问（10%）、法律顾问（5%）、金融业务顾问（5%）。AI Agent 是分工角色，不是 11 个真人；邝振华对所有 AI Agent 产出负终审责任，关键决策（架构、合规、商业）由邝振华拍板。此模式带来独特风险（见 §4.3）。

### 2.1 识别方法

| 方法 | 适用场景 | 责任人 |

### 3.1 概率评级

| 概率 | 描述 | 分值 |
|------|------|------|
| 极高 | > 70% 发生 | 5 |
| 高 | 50%-70% | 4 |
| 中 | 30%-50% | 3 |
| 低 | 10%-30% | 2 |
| 极低 | < 10% | 1 |

### 3.2 影响评级

| 影响 | 描述 | 分值 |
|------|------|------|
| 灾难 | 项目失败 / 上线延期 > 1 月 / 损失 > 100 万 | 5 |

| 中等 | 次要功能受损 / 延期 1-2 周 / 损失 5-30 万 | 3 |
| 轻微 | 体验问题 / 延期 < 1 周 / 损失 < 5 万 | 2 |
| 微小 | 几乎无影响 | 1 |

### 3.3 风险等级矩阵（V1.1 已修正数学）

> **V1.1 修正说明**：风险等级 = 概率 × 影响。V1.0 矩阵存在系统性数学错误（如概率 4 × 影响 3 = 12 应为"高"，V1.0 误标"中"），现按以下规则统一重算：
> - **1-4 = 低（LOW）**
> - **5-9 = 中（MEDIUM）**
> - **10-14 = 高（HIGH）**
> - **15-25 = 极高（CRITICAL）**

#### 3.3.1 修正后风险等级矩阵

```
                     影响
            1      2      3      4      5
概 5  [中=5 ] [高=10] [极高=15] [极高=20] [极高=25]
率 4  [低=4 ] [中=8 ] [高=12 ] [极高=16] [极高=20]
   3  [低=3 ] [中=6 ] [中=9 ] [高=12 ] [极高=15]
   2  [低=2 ] [低=4 ] [中=6 ] [中=8 ] [高=10 ]
   1  [低=1 ] [低=2 ] [低=3 ] [低=4 ] [中=5 ]
```

#### 3.3.2 修正后等级与处理策略

| 等级 | 风险值（概率×影响） | 处理策略 | 复核频率 |
|------|---------------------|----------|----------|

| 高（HIGH） | 10-14 | 必须缓解，每两周复核 | 每周监控 + 每两周复核 |
| 中（MEDIUM） | 5-9 | 应缓解，每月复核 | 每两周监控 + 每月复核 |
| 低（LOW） | 1-4 | 监控即可，每季度复核 | 每月监控 + 每季度复核 |

## 5. 技术风险

### 5.1 R-01: 数据质量不达标

**风险描述**：客户提供的历史交易数据可能存在字段缺失、标签噪声、样本不均衡等问题，导致 ML 模型训练不充分，AUC < 0.90。

**触发条件**：
- 数据缺失率 > 20%
- 欺诈样本占比 < 0.1%
- 标签错误率 > 5%

**影响**：
- 模型 AUC 不达标 → 拦截率低 / 误报率高
- 客户体验差 → 项目验收困难
- 需要追加数据清洗工作 → 进度延期

**应对策略**：
- **预防**：项目启动后立即开始数据质量评估，签订数据质量 SLA
- **缓解**：
  - 数据清洗流水线（去重、缺失值填充、异常值处理）
  - 合成数据生成（CTGAN / SMOTE）补充少数类
  - 引入公开数据集（如 IEEE-CIS Fraud Detection）预训练
- **应急**：模型回退到规则为主模式，ML 作为辅助
- **备份**：联系 1-2 个备选客户作为数据补充源

**监控指标**：
- 数据缺失率
- 标签分布
- 模型 AUC（每日监控）
- 模型漂移 PSI

### 5.2 R-03 / R-002: 评分延迟不达标（V1.1 升级为极高）

**风险描述**：评分接口 P99 > 200ms（违反基准 §2.1），无法满足客户实时反欺诈需求。V1.1 将此风险升级为 Top 5 极高（R-002，风险值 15）。

**触发条件**：
- TPS > 2000 时 P99 > 200ms
- ML 推理延迟 > 100ms
- 规则执行延迟 > 50ms

**影响**：
- 客户交易被阻断或延迟 → 业务损失
- 客户满意度下降 → 项目验收受阻
- 紧急性能优化 → 进度延误

**应对策略**：
- **预防**：
  - 架构设计阶段即考虑性能（异步、缓存、批处理）
  - 性能测试早介入（Sprint 4 开始）
- **缓解**：
  - Redis 缓存热数据（商户风险、用户画像）
  - ML 模型蒸馏 + 量化
  - 规则引擎编译优化（DSL → AST → 字节码）
  - 数据库读写分离 + 索引优化
- **应急**：启用降级模式（部分交易走纯规则），Kill Switch 关闭 ML
- **备份**：保留性能优化专项预算

### 5.3 R-05: GNN 大图 OOM

**风险描述**：Neo4j 子图查询或 GNN 推理在节点数 > 10万时内存溢出。

**应对**：
- 子图查询限制深度（≤ 3 跳）+ 节点数（≤ 1万）
- GNN 推理采用批处理 + 增量计算
- Neo4j 配置堆内存 ≥ 16GB
- 备选：图数据库切换到 TigerGraph 或 JanusGraph

### 5.4 R-10: 模型漂移

**风险描述**：欺诈模式变化导致模型 AUC 下降，PSI > 0.25。

**应对**：
- 实时漂移检测（PSI / KL / KS）
- 漂移告警触发自动再训练流水线
- 多模型并行（生产 + 金丝雀 + 影子）
- 模型回退策略（BERT → TF-IDF → 启发式）

### 5.5 R-14: 规则 DSL 注入

**风险描述**：恶意用户通过规则 DSL 执行 SQL 注入或代码注入。

**应对**：
- DSL 解析器沙箱化（无文件/网络/系统调用访问）
- 严格语法校验 + AST 白名单
- DSL 试运行在隔离环境
- 渗透测试覆盖

### 5.6 R-15: K8s 故障切换失败

**风险描述**：多 AZ 部署在某 AZ 故障时切换失败，导致服务中断。

**应对**：
- Pod 健康检查（liveness + readiness）
- 跨 AZ 反亲和性调度
- 数据库主从自动切换（Patroni）
- 定期混沌工程演练（每月一次）
- 故障恢复 SLA：RTO < 5min（应用层），总体 RTO ≤ 30min，RPO ≤ 1min（对齐基准 §2.1）

### 5.7 R-19: Neo4j 查询超时

**风险描述**：复杂子图查询超时，影响 GNN 服务可用性。

**应对**：
- 节点/关系索引优化
- 查询超时限制（默认 30s）
- 大查询降级（减少深度 / 节点数）
- 引入 Redis 缓存热点子图

## 6. 业务风险

### 6.1 R-04: 需求变更频繁

**风险描述**：客户在开发过程中频繁变更需求，导致范围蔓延、进度延误。

**应对**：
- 需求基线后变更必须走 CCB 流程
- 每次变更评估影响（进度、成本、风险）
- 高频变更引入变更费用条款
- Sprint 评审明确下一 Sprint 范围

### 6.2 R-13: 误报率过高

**风险描述**：上线后规则 / 模型误报率 > 30%（生产目标 ≤ 5%，试运行过渡期 ≤ 10%，对齐基准 §2.1），客户体验差，可能要求回滚。

**应对**：
- 灰度上线（5% → 25% → 100%）
- 每日误报率监控 + 告警
- 反馈闭环：分析师标记误报 → 规则/模型优化
- 应急：误报率 > 50% 触发自动降级

### 6.3 R-17: 客户对金丝雀机制不信任

**风险描述**：客户不理解金丝雀发布，认为风险大，拒绝推进。

**应对**：
- 上线前培训客户（含 demo）
- 透明告警：金丝雀启动/推进/回滚全部通知
- 文档化：金丝雀机制说明 + 应急预案
- 客户可随时叫停金丝雀

## 7. 合规风险

### 7.1 R-02: PCI-DSS 审计延迟

**风险描述**：PCI-DSS v4.0 审计排期延迟，导致无法在 02-28 前获得合规认证，影响上线。

**应对**：
- 提前 3 个月预约审计机构
- 内部预审计（09 月、12 月各一次）
- 准备审计材料清单（持续更新）
- 备选：与备选审计机构签订备用合同

### 7.2 R-08: 反洗钱监管接口对接延迟

**风险描述**：反洗钱上报接口审批时间长，导致无法按时上报。

**应对**（对齐基准 §7.3 统一口径）：
- 提前 6 个月提交接口申请
- 与监管机构建立沟通渠道
- Mock 接口先行开发
- 上线时如未对接，先本地生成报告，事后补报
- **范围说明**：FRD 完成 AML 报告生成与接口对接联调，上报通道本体由客户/第三方提供

### 7.3 R-18: PIPL 请求处理不及时

**风险描述**：用户提交个人信息导出/删除请求后，30 天内未响应，违反 PIPL。

**应对**（对齐基准 §7.1 PIPL 数据主体权利接口）：
- 建立请求处理流程与 SLA
- 工单系统自动跟踪
- 每周合规审计员检查未处理请求
- 自动化工具：数据导出脚本 + 数据删除脚本
- 实现基准 §7.1 全部 6 个接口（export-requests / deletion-requests / consent）

### 7.4 R-001: PCI-DSS v4.0 评估不通过（V1.1 新增，Top 5 极高）

**风险描述**：QSA 季度评估发现重大不符合项（如 CDE 范围过大、Tokenization 自建不达标、日志留存不足），无法取得 AOC（Attestation of Compliance），致 M7 生产部署准出失败、客户无法上线。

**触发条件**：
- QSA 评估报告列明任一 PCI-DSS v4.0 核心要求为"不符合"
- 自建 Tokenization 未通过独立安全评估
- CDE 范围扩散至非必要组件

**影响**（风险值 4×5=20，极高）：
- M7 准出失败 → 上线延期 > 1 月
- 客户合同违约 → 损失 > 100 万
- 需紧急整改 → 预算超支

**应对策略**：
- **规避**：CDE 范围最小化（仅保留评分必需的卡数据流）；Tokenization 优先采用阿里云 KMS（对齐基准 §8.4）降低自建合规风险
- **缓解**：M3 即完成 PCI-DSS 隔离区方案评审；季度内部预评估；SEC Agent 持续监控 12 项核心要求
- **转移**：QSA 顾问整改指导（外聘，预算 250000 元，对齐基准 §6.1）
- **应急**：启动 PCI-DSS 评估不通过 Plan B（见 §14.4）

**责任人**：邝振华（真人终审）+ SEC Agent + QSA 顾问

### 7.5 R-003: 等保 2.0 三级备案失败（V1.1 新增，Top 5 极高）

**风险描述**：测评机构对 GB/T 22239 等保 2.0 三级测评未通过（物理/网络/主机/应用/数据/管理 6 类控制点存在重大不符合），无法取得备案证明，致 M5（Beta 准出）与 M7（生产部署）失败。

**触发条件**：
- 测评机构出具整改通知书，关键控制点不达标
- M1（2026-08-15）未启动备案（周期 3-6 个月，对齐基准 §5）
- 安全管理中心/剩余信息保护项缺失

**影响**（风险值 3×5=15，极高）：
- M5/M7 准出失败 → 上线延期 ≥ 3 月
- 监管处罚风险
- 客户拒绝验收

**应对策略**：
- **缓解**：M1 即启动备案；6 类控制点预测评（M2 前完成差距分析）；对齐基准 §7.2 实现全部控制点
- **转移**：测评机构费用 100000 元（对齐基准 §6.1）
- **应急**：联系备选测评机构；范围分阶段备案（先非 CDE，后 CDE）
- **监控**：6 类控制点符合率每月自评

**责任人**：邝振华（真人）+ SEC Agent + 测评机构

## 8. 安全风险

### 8.1 R-06: 多租户数据隔离失效

**风险描述**：因代码缺陷或配置错误，租户 A 能访问租户 B 的数据。

**影响**：客户数据泄露 → 法律责任 + 信誉损失

**应对**：
- 行级隔离：所有查询强制 `WHERE tenant_id = ?`
- ORM 层强制注入 tenant_id
- PostgreSQL RLS（对齐基准 §4.3）
- 单元测试覆盖（跨租户访问必须 404）
- 渗透测试（每次发版前）
- 第三方安全审计

### 8.2 R-07: PII 数据泄露

**风险描述**：持卡人姓名、手机号、卡号等 PII 数据因代码缺陷或攻击泄露。

**应对**：
- PII 字段 Fernet 加密落库
- API 响应脱敏（手机号中间 4 位、姓名首字）
- 日志脱敏（敏感字段不记录或脱敏）
- 访问审计：所有 PII 访问记录到审计日志
- 最小权限：仅必要角色可访问明文

### 8.3 R-14: DSL 注入攻击

详见 §5.5。

### 8.4 其他安全风险

| 风险 | 应对 |
|------|------|
| JWT 伪造 | RS256 签名 + 短时效 + 黑名单 |
| SQL 注入 | 参数化查询 + ORM |
| XSS | 输入消毒 + CSP |
| CSRF | Token + SameSite Cookie |
| 暴力破解 | 限流 + 账号锁定 |
| DDoS | 阿里云 DCDN + WAF + DDoS 高防（对齐基准 §8.4，不用 Cloudflare） |
| 内部威胁（含 AI Agent） | 最小权限 + 审计 + 职责分离 + RBAC（对齐 R-AI-04） |

| 测试环境不足 | 容器化 + 按需创建 |
| 工具许可证不足 | 提前采购 + 评估开源替代 |
| LLM API 配额不足 | 多供应商（通义/文心/DeepSeek，对齐基准 §7.4）+ 降级 |

### 9.4 R-004: 11 AI Agent 协作失控（V1.1 新增，Top 5 极高）

**风险描述**：11 个 AI Agent 在分工协作中因决策冲突、上下文丢失、依赖死锁等原因，致产出无法合入主线或相互覆盖，项目停摆。此风险是 1 真人 + 11 AI Agent 模式的系统性风险（详见 §4.3 七条子风险）。

**触发条件**：
- 多个 Agent 同时修改同一模块，产生覆盖
- 决策冲突未在 48h 内仲裁
- DAG 编排出现死锁，流水线停滞 > 4h
- 真人（邝振华）review 积压 > 50 个 PR

**影响**（风险值 4×4=16，极高）：
- 产出质量下降 → 集成测试失败率上升
- 进度延期 > 2 周
- 真人精力瓶颈 → 决策阻塞

**应对策略**：
- **缓解**：
  - 决策仲裁器：PM Agent 仲裁冲突，邝振华真人终审（对齐基准 §1.4）
  - DAG 任务编排：PM Agent 拓扑排序，禁止环，超时熔断（见 R-AI-06）
  - RBAC + 分支保护：每个 Agent 仅可写授权路径（见 R-AI-04）
  - review SLA：邝振华每日固定时段集中 review，PR 积压超阈值时降低 Agent 并发度
- **应急**：暂停非关键 Agent，集中真人 + PM + ARCH + QA 四角色推进关键路径
- **监控**：PR 积压数、仲裁响应时长、DAG 排队时长、返工率

**责任人**：邝振华（真人终审）+ PM Agent（编排仲裁）

### 9.5 R-005: 单人（邝振华）单点故障（V1.1 新增，Top 5 极高）

**风险描述**：邝振华是项目唯一真人决策者（100% 投入），一旦发生伤病、精力瓶颈、个人事务中断，所有 AI Agent 产出无法合入主线，关键决策（架构/合规/商业）阻塞，项目停摆。

**触发条件**：
- 邝振华连续 > 3 天无法 review
- 关键决策（如 PCI-DSS 范围、模型上线）积压 > 5 项
- 真人健康/精力指标异常

**影响**（风险值 3×5=15，极高）：
- 决策阻塞 → 进度延期 > 1 月
- AI Agent 产出无人合入 → 工作堆积失效
- 客户/监管沟通中断

**应对策略**：
- **缓解**：
  - 关键决策文档化：所有决策标准、阈值、授权矩阵预定义，AI Agent 在授权区间内自主执行
  - AI Agent 自主执行区间：非关键路径（如 UI 调整、测试补全）无须逐项真人审批
  - 外聘顾问备份：QSA 顾问（合规决策备份）、法律顾问（法务决策备份）、金融业务顾问（业务决策备份）可在真人缺席时提供专业意见
  - 健康管理：邝振华保持合理工作节奏，避免长期过劳
- **应急**：授权 PM Agent + ARCH Agent + SEC Agent 三人小组在真人短期缺席（≤ 2 周）时维持低风险运营；超过 2 周启动顾问代行机制
- **监控**：决策积压数、review SLA 达成率、真人可用率

**责任人**：邝振华（真人）+ PM Agent（监控预警）

## 11. 运营风险

### 11.1 R-20: 告警疲劳

**风险描述**：监控告警过多导致运维人员忽视关键告警。

**应对**：
- 告警分级（INFO/WARN/CRITICAL）

**风险描述**：上线后系统稳定性不足，频繁故障。

**应对**（对齐基准 §2.1 SLA 99.5%/99.9% 与 §8.2 灰度）：
- 灰度上线（5% 24h → 25% 24h → 100% 72h）
- 7×24 试点运维（首月）
- 故障应急预案
- 故障复盘机制
- SLA 目标：99.5%（MVP），试运行后升级至 99.9%

### 11.3 可维护性

**风险描述**：代码质量差导致后续维护成本高。

**应对**：
- 代码评审（每个 PR，邝振华 + QA Agent）
- 静态扫描（Ruff / ESLint / Bandit）
- 单元测试覆盖率 ≥ 90%（评分/规则引擎核心，对齐基准 §2.1）
- 文档化（API、架构、操作手册）

## 14. 应急响应预案

### 14.1 应急级别

| 级别 | 描述 | 响应时间 | 决策人 |
|------|------|----------|--------|
| L1 | 一般问题 | 4h | PM Agent |
| L2 | 严重问题 | 1h | 邝振华（技术负责人） |
| L3 | 重大事故 | 15min | 邝振华 + 客户 |
| L4 | 灾难 | 立即 | 邝振华 + 客户 + 监管 |

### 14.2 应急流程

```
1. 事件检测（监控告警 / 用户反馈）
2. 初步评估（级别判定）
3. 启动应急响应（组建应急小组）
4. 紧急处置（止损 + 修复）
5. 沟通通知（内部 + 客户 + 监管）
6. 恢复验证
7. 事后复盘
8. 改进措施落实
```

### 14.3 典型应急预案

#### 14.3.1 数据泄露应急

1. **立即**（15min）：阻断泄露源（关闭接口、吊销 token）
2. **30min**：评估泄露范围（哪些数据、多少用户）
3. **1h**：通知合规负责人（SEC Agent）+ 邝振华
4. **24h**：通知受影响用户（如 PIPL 要求）
5. **72h**：通知监管部门（如适用）
6. **7 天**：提交事件报告
7. **30 天**：完成整改并验证

#### 14.3.2 系统宕机应急

1. **立即**：自动故障切换（K8s / 数据库主从）
2. **5min**：运维确认切换成功
3. **15min**：如未恢复，启动备用方案（Kill Switch 降级）
4. **30min**：通知客户
5. **1h**：根因分析
6. **2h**：修复或回滚
7. **24h**：复盘报告

#### 14.3.3 模型异常应急

1. **立即**：自动触发金丝雀回滚
2. **5min**：运维确认回滚成功
3. **15min**：ML Agent 介入分析
4. **30min**：如未恢复，启用 Kill Switch
5. **1h**：通知客户
6. **24h**：根因分析 + 改进措施

### 14.4 PCI-DSS 评估不通过 Plan B（V1.1 新增）

> **触发条件**：QSA 季度评估发现重大不符合项，无法取得 AOC，R-001 风险发生。

**应急措施**：

| 序号 | 措施 | 详情 | 时间线 |
|------|------|------|--------|
| a | 评估范围降级 | CDE 范围进一步收缩到最小集（仅评分必需卡数据流），剥离非必要组件至非 CDE 区，降低评估复杂度 | 评估不通过 → 7 天内完成 |
| b | Tokenization 服务紧急替换 | 自建 Tokenization → 阿里云 KMS Tokenization（对齐基准 §8.4），消除自建合规风险，由云厂商承担部分合规责任 | 7-14 天内完成切换 + 联调 |
| c | 临时隔离 CDE，业务降级 | 临时隔离 CDE 区，业务降级到纯规则引擎模式（关闭 ML 推理），保证基本交易风控可用 | 24h 内启动降级 |
| d | 与 QSA 协商整改计划 | 与 QSA 顾问协商分阶段整改计划（90 天短期整改 + 180 天长期达标），争取有条件 AOC | 30 天内提交整改计划 |
| e | 客户沟通 | 暂停新客户接入；存量客户签署知情同意书，告知临时降级与整改时间表 | 评估不通过 → 7 天内通知 |

**责任人**：邝振华（真人，总指挥）+ SEC Agent（合规执行）+ QSA 顾问（整改指导）+ 法务顾问（客户沟通）

**时间线总览**：
```
评估不通过（T0）
   ↓ 24h 内
启动 Plan B + CDE 临时隔离 + 业务降级到纯规则
   ↓ 7 天内
完成 CDE 范围降级 + 客户沟通
   ↓ 14 天内
完成 Tokenization 切换阿里云 KMS + 联调
   ↓ 30 天内
向 QSA 提交整改计划（90/180 天）
   ↓ 90 天
短期整改完成，QSA 复评
   ↓ 180 天
长期达标，取得正式 AOC
```

**预算来源**：QSA 顾问预算 250000 元（基准 §6.1）+ 应急储备金 52250 元（§12.3）。

4. 经验教训沉淀到组织过程资产

## 15. 风险闭环管理

### 15.1 风险生命周期

```
识别 → 评估 → 应对 → 监控 → 复盘 → 关闭
              ↑                    │
              └────── 重新评估 ←───┘
```

### 15.2 关闭条件

风险满足以下条件之一可关闭：

- 风险源已消除（如变更需求被拒绝）
- 概率降至极低（< 5%）
- 已发生并完成处置
- 项目结束

### 15.3 经验教训沉淀

每月复盘：

- 已发生风险的处理效果
- 新增风险的识别
- 应对策略的有效性
- 改进措施

经验教训沉淀到组织过程资产，作为后续项目参考。
