## 1. 风险评估概述

### 1.1 评估目的

- 系统识别 FRD 项目全生命周期内的潜在风险
- 量化风险概率与影响，明确优先级
- 制定可执行的应对策略与应急预案
- 建立风险监控与闭环机制

### 1.2 评估范围

- 项目级风险：进度、成本、资源、范围
- 技术风险：架构、性能、可靠性
- 业务风险：需求、用户体验、市场
- 合规风险：PCI-DSS、PIPL、反洗钱法
- 安全风险：数据泄露、攻击、滥用
- 运营风险：上线后稳定性、可维护性

### 1.3 评估时间

- 初评：2026-07-27（项目立项）
- 复评：每月一次（与月度评审同步）
- 专项评估：里程碑节点、重大变更、安全事件后

## 2. 风险识别方法

### 2.1 识别方法

| 方法 | 适用场景 | 责任人 |
|------|----------|--------|
| 头脑风暴 | 项目初期广泛识别 | PM 主持，全员参与 |

- 内部：人员、流程、技术、资源
- 外部：客户、监管、市场、第三方
- 历史：同类项目经验教训
- 假设：项目假设失效带来的风险

## 3. 风险评估标准

### 3.1 概率评级

| 概率 | 描述 | 分值 |
|------|------|------|
| 极高 | > 70% 发生 | 5 |
| 高 | 50%-70% | 4 |
| 中 | 30%-50% | 3 |
| 低 | 10%-30% | 2 |
| 极低 | < 10% | 1 |

### 3.2 影响评级

| 影响 | 描述 | 分值 |
|------|------|------|
| 灾难 | 项目失败 / 上线延期 > 1 月 / 损失 > 100 万 | 5 |
| 严重 | 主要功能受损 / 延期 2-4 周 / 损失 30-100 万 | 4 |
| 中等 | 次要功能受损 / 延期 1-2 周 / 损失 5-30 万 | 3 |
| 轻微 | 体验问题 / 延期 < 1 周 / 损失 < 5 万 | 2 |
| 微小 | 几乎无影响 | 1 |

### 3.3 风险等级矩阵

```
                影响
        1    2    3    4    5
概 5  [低] [中] [高] [极高][极高]
率 4  [低] [中] [中] [高] [极高]
   3  [低] [低] [中] [中] [高]
   2  [低] [低] [低] [中] [中]
   1  [低] [低] [低] [低] [低]
```

| 等级 | 风险值 | 处理策略 |
|------|--------|----------|
| 极高 | ≥ 16 | 必须规避或转移，每周复核 |
| 高 | 10-15 | 必须缓解，每两周复核 |
| 中 | 6-9 | 应缓解，每月复核 |
| 低 | ≤ 5 | 监控即可，每季度复核 |

## 5. 技术风险

### 5.1 R-01: 数据质量不达标

**风险描述**：客户提供的历史交易数据可能存在字段缺失、标签噪声、样本不均衡等问题，导致 ML 模型训练不充分，AUC < 0.90。

**触发条件**：
- 数据缺失率 > 20%
- 欺诈样本占比 < 0.1%
- 标签错误率 > 5%

**影响**：
- 模型 AUC 不达标 → 拦截率低 / 误报率高
- 客户体验差 → 项目验收困难
- 需要追加数据清洗工作 → 进度延期

**应对策略**：
- **预防**：项目启动后立即开始数据质量评估，签订数据质量 SLA
- **缓解**：
  - 数据清洗流水线（去重、缺失值填充、异常值处理）
  - 合成数据生成（CTGAN / SMOTE）补充少数类
  - 引入公开数据集（如 IEEE-CIS Fraud Detection）预训练
- **应急**：模型回退到规则为主模式，ML 作为辅助
- **备份**：联系 1-2 个备选客户作为数据补充源

**监控指标**：
- 数据缺失率
- 标签分布
- 模型 AUC（每日监控）
- 模型漂移 PSI

### 5.2 R-03: 评分延迟不达标

**风险描述**：评分接口 P99 > 200ms，无法满足客户实时反欺诈需求。

**触发条件**：
- TPS > 2000 时 P99 > 200ms
- ML 推理延迟 > 100ms
- 规则执行延迟 > 50ms

**影响**：
- 客户交易被阻断或延迟 → 业务损失
- 客户满意度下降 → 项目验收受阻
- 紧急性能优化 → 进度延误

**应对策略**：
- **预防**：
  - 架构设计阶段即考虑性能（异步、缓存、批处理）
  - 性能测试早介入（Sprint 4 开始）
- **缓解**：
  - Redis 缓存热数据（商户风险、用户画像）
  - ML 模型蒸馏 + 量化
  - 规则引擎编译优化（DSL → AST → 字节码）
  - 数据库读写分离 + 索引优化
- **应急**：启用降级模式（部分交易走纯规则），Kill Switch 关闭 ML
- **备份**：保留性能优化专项预算

### 5.3 R-05: GNN 大图 OOM

**风险描述**：Neo4j 子图查询或 GNN 推理在节点数 > 10万时内存溢出。

**应对**：
- 子图查询限制深度（≤ 3 跳）+ 节点数（≤ 1万）
- GNN 推理采用批处理 + 增量计算
- Neo4j 配置堆内存 ≥ 16GB
- 备选：图数据库切换到 TigerGraph 或 JanusGraph

### 5.4 R-10: 模型漂移

**风险描述**：欺诈模式变化导致模型 AUC 下降，PSI > 0.25。

**应对**：
- 实时漂移检测（PSI / KL / KS）
- 漂移告警触发自动再训练流水线
- 多模型并行（生产 + 金丝雀 + 影子）
- 模型回退策略（BERT → TF-IDF → 启发式）

### 5.5 R-14: 规则 DSL 注入

**风险描述**：恶意用户通过规则 DSL 执行 SQL 注入或代码注入。

**应对**：
- DSL 解析器沙箱化（无文件/网络/系统调用访问）
- 严格语法校验 + AST 白名单
- DSL 试运行在隔离环境
- 渗透测试覆盖

### 5.6 R-15: K8s 故障切换失败

**风险描述**：多 AZ 部署在某 AZ 故障时切换失败，导致服务中断。

**应对**：
- Pod 健康检查（liveness + readiness）
- 跨 AZ 反亲和性调度
- 数据库主从自动切换（Patroni）
- 定期混沌工程演练（每月一次）
- 故障恢复 SLA：RTO < 5min，RPO < 1min

### 5.7 R-19: Neo4j 查询超时

**风险描述**：复杂子图查询超时，影响 GNN 服务可用性。

**应对**：
- 节点/关系索引优化
- 查询超时限制（默认 30s）
- 大查询降级（减少深度 / 节点数）
- 引入 Redis 缓存热点子图

## 6. 业务风险

### 6.1 R-04: 需求变更频繁

**风险描述**：客户在开发过程中频繁变更需求，导致范围蔓延、进度延误。

**应对**：
- 需求基线后变更必须走 CCB 流程
- 每次变更评估影响（进度、成本、风险）
- 高频变更引入变更费用条款
- Sprint 评审明确下一 Sprint 范围

### 6.2 R-13: 误报率过高

**风险描述**：上线后规则 / 模型误报率 > 30%，客户体验差，可能要求回滚。

**应对**：
- 灰度上线（5% → 25% → 100%）
- 每日误报率监控 + 告警
- 反馈闭环：分析师标记误报 → 规则/模型优化
- 应急：误报率 > 50% 触发自动降级

### 6.3 R-17: 客户对金丝雀机制不信任

**风险描述**：客户不理解金丝雀发布，认为风险大，拒绝推进。

**应对**：
- 上线前培训客户（含 demo）
- 透明告警：金丝雀启动/推进/回滚全部通知
- 文档化：金丝雀机制说明 + 应急预案
- 客户可随时叫停金丝雀

## 7. 合规风险

### 7.1 R-02: PCI-DSS 审计延迟

**风险描述**：PCI-DSS v4.0 审计排期延迟，导致无法在 02-28 前获得合规认证，影响上线。

**应对**：
- 提前 3 个月预约审计机构
- 内部预审计（09 月、12 月各一次）
- 准备审计材料清单（持续更新）
- 备选：与备选审计机构签订备用合同

### 7.2 R-08: 反洗钱监管接口对接延迟

**风险描述**：反洗钱上报接口审批时间长，导致无法按时上报。

**应对**：
- 提前 6 个月提交接口申请
- 与监管机构建立沟通渠道
- Mock 接口先行开发
- 上线时如未对接，先本地生成报告，事后补报

### 7.3 R-18: PIPL 请求处理不及时

**风险描述**：用户提交个人信息导出/删除请求后，30 天内未响应，违反 PIPL。

**应对**：
- 建立请求处理流程与 SLA
- 工单系统自动跟踪
- 每周合规审计员检查未处理请求
- 自动化工具：数据导出脚本 + 数据删除脚本

## 8. 安全风险

### 8.1 R-06: 多租户数据隔离失效

**风险描述**：因代码缺陷或配置错误，租户 A 能访问租户 B 的数据。

**影响**：客户数据泄露 → 法律责任 + 信誉损失

**应对**：
- 行级隔离：所有查询强制 `WHERE tenant_id = ?`
- ORM 层强制注入 tenant_id
- 单元测试覆盖（跨租户访问必须 404）
- 渗透测试（每次发版前）
- 第三方安全审计

### 8.2 R-07: PII 数据泄露

**风险描述**：持卡人姓名、手机号、卡号等 PII 数据因代码缺陷或攻击泄露。

**应对**：
- PII 字段 Fernet 加密落库
- API 响应脱敏（手机号中间 4 位、姓名首字）
- 日志脱敏（敏感字段不记录或脱敏）
- 访问审计：所有 PII 访问记录到审计日志
- 最小权限：仅必要角色可访问明文

### 8.3 R-14: DSL 注入攻击

详见 §5.4。

### 8.4 其他安全风险

| 风险 | 应对 |
|------|------|
| JWT 伪造 | RS256 签名 + 短时效 + 黑名单 |
| SQL 注入 | 参数化查询 + ORM |
| XSS | 输入消毒 + CSP |
| CSRF | Token + SameSite Cookie |
| 暴力破解 | 限流 + 账号锁定 |
| DDoS | CDN + WAF + 流量清洗 |
| 内部威胁 | 最小权限 + 审计 + 职责分离 |

## 9. 进度与资源风险

### 9.1 R-09: 团队成员流失

**风险描述**：关键人员（特别是 ML 工程师）离职导致知识断层。

**应对**：
- 知识共享：每周技术分享
- 文档化：核心模块必须有详细文档
- 代码评审：至少 2 人熟悉每个模块
- 备份人员：识别每个角色的备份
- 留人：股权激励 / 项目奖金 / 成长机会

### 9.2 R-16: 关键路径延期

**风险描述**：关键路径任务延期导致整体上线延期。

**应对**：
- 关键路径任务每日监控
- 浮动 ≤ 0 时启动预警
- 赶工：加班 / 增加资源
- 快速跟进：并行原本串行的任务
- 范围协商：低优先级功能延期到 V1.1

### 9.3 其他资源风险

| 风险 | 应对 |
|------|------|
| 预算超支 | 月度预算审查 + 变更控制 |
| 云资源配额不足 | 提前申请 + 监控使用率 |
| 测试环境不足 | 容器化 + 按需创建 |
| 工具许可证不足 | 提前采购 + 评估开源替代 |

## 10. 第三方依赖风险

### 10.1 R-11: 设备指纹 SDK 集成失败

**应对**：
- 提前 POC 验证（Sprint 2）
- 备选方案：同义词库自研 / 备选厂商
- 集成测试覆盖
- SDK 故障降级：缺失字段时模型仍可工作

### 10.2 R-12: IP 地理库滞后

**应对**：
- 双源备份（MaxMind + 自建）
- 每月数据校验
- 滞后字段不作为强阻断规则依据

### 10.3 其他第三方依赖

## 11. 运营风险

### 11.1 R-20: 告警疲劳

**风险描述**：监控告警过多导致运维人员忽视关键告警。

**应对**：
- 告警分级（INFO/WARN/CRITICAL）
- 静默规则（重复告警聚合）
- 智能告警（基于历史基线）
- 告警 SLO：CRITICAL 必须 5 分钟内响应

### 11.2 上线后稳定性

**风险描述**：上线后系统稳定性不足，频繁故障。

**应对**：
- 灰度上线（5% → 25% → 100%）
- 7×24 试点运维（首月）
- 故障应急预案
- 故障复盘机制

### 11.3 可维护性

**风险描述**：代码质量差导致后续维护成本高。

**应对**：
- 代码评审（每个 PR）
- 静态扫描（Ruff / ESLint / Bandit）
- 单元测试覆盖率 ≥ 90%
- 文档化（API、架构、操作手册）

## 12. 风险应对策略

### 12.1 四大策略

| 策略 | 适用场景 | 典型措施 |
|------|----------|----------|
| 规避 | 高风险且可控 | 取消风险源、改用成熟方案 |
| 缓解 | 中高风险不可避免 | 降低概率/影响 |
| 转移 | 后果严重但可转移 | 保险、外包、合同条款 |
| 接受 | 低风险或成本过高 | 监控 + 应急预案 |

| R-02 PCI 审计 | 缓解 + 转移 | 提前预约 + 备选机构 |
| R-03 性能 | 缓解 | 早压测 + 缓存 + 优化 |

| R-15 K8s 故障 | 缓解 | 混沌工程 + 演练 |

## 13. 风险监控与预警

### 13.1 监控频率

| 风险等级 | 监控频率 | 复核人 |
|----------|----------|--------|
| 极高 | 每日 | PM |
| 高 | 每周 | PM + 责任人 |
| 中 | 每两周 | 责任人 |
| 低 | 每月 | 责任人 |

### 13.2 监控指标

| 风险类别 | 关键指标 | 预警阈值 |
|----------|----------|----------|
| 进度 | SPI | < 0.95 |
| 成本 | CPI | < 0.95 |
| 质量 | 缺陷密度 | > 5/千行 |
| 性能 | P99 延迟 | > 200ms |
| 安全 | 安全事件 | > 0 |
| 合规 | 合规违反 | > 0 |
| 漂移 | PSI | > 0.25 |
| 误报率 | 案件误报率 | > 30% |

### 13.3 风险预警机制

```
监控指标超阈值
   ↓
自动告警（邮件 + IM）
   ↓
责任人在 4h 内响应
   ↓
PM 评估是否升级
   ↓
如升级，启动应急响应
```

### 13.4 风险报告

- **周报**：风险概览（数量、等级变化、新增、关闭）
- **月报**：详细风险评估与应对进展
- **专项报告**：重大风险事件后立即生成

## 14. 应急响应预案

### 14.1 应急级别

| 级别 | 描述 | 响应时间 | 决策人 |
|------|------|----------|--------|
| L1 | 一般问题 | 4h | PM |
| L2 | 严重问题 | 1h | 技术负责人 |
| L3 | 重大事故 | 15min | 高管 + 客户 |
| L4 | 灾难 | 立即 | 高管 + 客户 + 监管 |

### 14.2 应急流程

```
1. 事件检测（监控告警 / 用户反馈）
2. 初步评估（级别判定）
3. 启动应急响应（组建应急小组）
4. 紧急处置（止损 + 修复）
5. 沟通通知（内部 + 客户 + 监管）
6. 恢复验证
7. 事后复盘
8. 改进措施落实
```

### 14.3 典型应急预案

#### 14.3.1 数据泄露应急

1. **立即**（15min）：阻断泄露源（关闭接口、吊销 token）
2. **30min**：评估泄露范围（哪些数据、多少用户）
3. **1h**：通知合规负责人 + 高管
4. **24h**：通知受影响用户（如 PIPL 要求）
5. **72h**：通知监管部门（如适用）
6. **7 天**：提交事件报告
7. **30 天**：完成整改并验证

#### 14.3.2 系统宕机应急

1. **立即**：自动故障切换（K8s / 数据库主从）
2. **5min**：运维确认切换成功
3. **15min**：如未恢复，启动备用方案（Kill Switch 降级）
4. **30min**：通知客户
5. **1h**：根因分析
6. **2h**：修复或回滚
7. **24h**：复盘报告

#### 14.3.3 模型异常应急

1. **立即**：自动触发金丝雀回滚
2. **5min**：运维确认回滚成功
3. **15min**：ML 工程师介入分析
4. **30min**：如未恢复，启用 Kill Switch
5. **1h**：通知客户
6. **24h**：根因分析 + 改进措施

## 15. 风险闭环管理

### 15.1 风险生命周期

```
识别 → 评估 → 应对 → 监控 → 复盘 → 关闭
              ↑                    │
              └────── 重新评估 ←───┘
```

### 15.2 关闭条件

风险满足以下条件之一可关闭：

- 风险源已消除（如变更需求被拒绝）
- 概率降至极低（< 5%）
- 已发生并完成处置
- 项目结束

### 15.3 经验教训沉淀

每月复盘：

- 已发生风险的处理效果
- 新增风险的识别
- 应对策略的有效性
- 改进措施

经验教训沉淀到组织过程资产，作为后续项目参考。
